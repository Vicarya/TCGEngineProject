# WeissBattleScene 詳細設計

最終更新: 2026-05-06

## 1. 目的

- `Assets/Scenes/WeissBattleScene.unity` を、見た目確認用のサンプルではなく、実際のヴァイスシュヴァルツ対戦を進行できる対戦シーンとして完成させる。
- 既存の `GameCore` / `WeissSchwarz` ロジックを活かしつつ、シーン、UI、プレイヤー制御、デッキロード、開始手順を本番導線として接続する。
- 進捗管理は `docs/TODO_ActionPlan.md` で行い、この文書は仕様が変わらない限り更新しない前提の固定仕様書とする。

## 2. 現状整理

### 2.1 実装済み

- `WeissBattleScene` は `SampleScene` 複製ベースで、対戦マットと各ゾーンUIの配置済み。
- ゾーン表示は概ね実装済み。
- `Hand/Stock/Clock/Level/Memory` はテンプレート座標差分によるずらし配置。
- `WaitingRoom` は同位置積み重ね表示。
- `Stage` は 5 固定スロット表示。
- `GameManager -> WeissGame -> WeissRuleEngine -> GameView` の更新導線は存在する。
- マリガン用モーダル、Yes/No モーダル、メインフェーズ選択モーダルの基礎は存在する。

### 2.2 未実装/暫定

- `WeissGame.SetupGame()` が `StreamingAssets/WeissSchwarz/Decks/deck1.txt` 固定読込。
- プレイヤー2が `ConsolePlayerController` 固定で、2PともシーンUIで進行する構成になっていない。
- 先攻後攻決定が未実装で、実質 `Players[0]` 開始。
- デッキ検証が未実装。
- `UIGamePlayerController` の多くがダミー戻り値。
- `GameView` はアクティブプレイヤー1人ぶん更新中心で、両プレイヤー同時可視化の責務が弱い。
- 対戦準備から終了までのシーン内ステート遷移が文書化されていない。
- NPC化を見据えた「定石ベース意思決定」レイヤーが無い。

## 3. 設計方針

### 3.1 シーンの責務

- `WeissBattleScene` は「対戦専用シーン」とする。
- デッキ選択、ゲーム生成、先攻後攻決定、初期手札、マリガン、ターン進行、勝敗表示までをこのシーンで完結させる。
- デッキ編集やカードDB閲覧は別シーン/別導線の責務とする。

### 3.2 ロジックの責務分離

- `WeissGame` は対戦セットアップとプレイヤー/ゾーン生成を担当する。
- `WeissRuleEngine` はルール進行、ドロー、ダメージ、リフレッシュ、レベルアップ、攻撃処理を担当する。
- `IWeissPlayerController` 実装は「選択」を担当する。
- `GameView` / 各 ZoneUI は表示と入力受付のみ担当する。
- デッキ構築/検証は専用サービスに分離し、`WeissGame.SetupGame()` の直書きをやめる。

### 3.3 NPC方針

- まずは「定石ベース」の簡易ロジックを実装する。
- 完全AIではなく、マリガン、レベルアップ、攻撃順、アタック種別、カウンター、アンコールを段階実装する。
- これはデバッグ用自動対戦・回帰確認・将来のNPC拡張の共通基盤として扱う。

## 4. 対戦フロー詳細

## フェーズ: 対戦準備

### 概要

- 対戦設定を読み込み、両プレイヤーのデッキを確定する。
- デッキ検証後、山札に配置してシャッフルする。
- 先攻後攻決定を行う。
- 初期手札5枚をドローする。
- マリガンを両プレイヤー分行う。
- 完了後、先攻プレイヤーのドローフェーズへ遷移する。

### 実装要件

- 対戦開始時に使用する 50 枚デッキデータを事前に用意する。
- 初期実装では「タイトルごとの固定サンプルデッキ選択」でよい。
- 1デッキは以下を満たすこと。
- 合計 50 枚。
- 同名カード 4 枚まで。
- ルール上の構成違反があれば対戦開始前に不正と判定する。
- 不正デッキ時は即敗北または開始拒否とする。
- 先攻後攻決定は、先攻カード1枚・後攻カード1枚を並べてランダムに1枚引く仕様で実装する。
- 初期手札は山札上から 5 枚。
- マリガンは選択カードを控え室へ送り、同枚数を山札から引く。
- 初期NPCは「レベル0以外を優先してマリガン」が基本戦略。

### テスト

- ゲーム開始時に設定した 50 枚が正しくロードされる。
- 50 枚未満/超過、同名 5 枚以上などの不正デッキを検知できる。
- 先攻後攻カードからランダムに 1 枚選ばれ、先攻/後攻が正しく反映される。
- 両プレイヤーが山札上から 5 枚引いて手札を作る。
- マリガン対象カードが控え室へ送られ、差分枚数ぶんドローされる。
- 両プレイヤーのマリガン完了後、先攻プレイヤーのドローフェーズへ遷移する。

## フェーズ: ターン開始

### 概要

- アクティブプレイヤーを確定し、ターン状態を初期化する。
- レスト状態、ターン内フラグ、誘発待ちキューなどを整理する。

### 実装要件

- `ResetTurnState()` を UI/NPC 両コントローラで意味のある初期化にする。
- ターン開始時イベントを発行し、UI に現在手番を反映する。

### テスト

- ターンプレイヤーが切り替わる。
- レスト解除や一時バフ解除などのターン開始処理が走る。

## フェーズ: ドローフェーズ

### 概要

- ターンプレイヤーが山札から 1 枚引く。
- リフレッシュ発生時は既存ロジックを通して処理する。

### 実装要件

- `WeissRuleEngine.DrawCard()` を標準導線として使用する。
- UI に手札増加、山札枚数変化、リフレッシュダメージを反映する。

### テスト

- 通常ドローできる。
- 山札切れ時に控え室からリフレッシュされ、リフレッシュポイントダメージが入る。

## フェーズ: クロックフェーズ

### 概要

- 手札から 1 枚をクロックに置くか選択する。
- 置いた場合は 2 枚ドローする。

### 実装要件

- UIプレイヤーは手札選択UIを使う。
- NPCは基本的に不要牌を優先してクロックする。
- 置かない選択も可能にする。

### テスト

- クロックする/しないの選択ができる。
- クロックしたカードがクロックへ移動し、2 枚引ける。

## フェーズ: メインフェーズ

### 概要

- プレイ、起動能力、クライマックス配置、能力使用、終了選択を行う。

### 実装要件

- `ChooseMainPhaseAction()` を本実装にする。
- プレイ可能スロットとコスト支払いを UI から選べるようにする。
- `UIGamePlayerController` の以下を段階実装する。
- `ChooseCardFromHand`
- `ChooseClimaxFromHand`
- `ChooseAbilityToActivate`
- `ChooseTargetCard`
- `SelectCardsToPayCost`

### テスト

- 手札からキャラ/クライマックスを適切なゾーンへ置ける。
- 使用可能能力のみ選択肢に出る。
- コスト不足時は実行できない。

## フェーズ: アタックフェーズ

### 概要

- アタッカー選択、攻撃種別選択、トリガー、ダメージ、カウンター、バトル、アンコールを処理する。

### 実装要件

- `ChooseAttacker`
- `ChooseAttackType`
- `ChooseCounterCardFromHand`
- `ChooseToEndAttack`
- `ChooseToEncore`
- `ChooseLevelUpCard`
- `ChooseAbilityToResolve`
  を本実装にする。
- NPCは以下の簡易定石でよい。
- 前列から優先攻撃。
- 正面がいるならフロント、いなければダイレクト。
- 条件を満たすカウンターを優先。
- 重要キャラのみアンコール。

### テスト

- 攻撃対象と攻撃種別を正しく選べる。
- トリガー処理、ダメージ処理、キャンセル処理が流れる。
- カウンターとアンコールが分岐どおりに処理される。

## フェーズ: エンドフェーズ

### 概要

- ターン終了処理を行い、次プレイヤーへ手番を渡す。

### 実装要件

- ターン一時状態をクリアする。
- 勝敗未決なら次ターンへ進む。

### テスト

- 手番が交代する。
- ターン制限状態が残らない。

## フェーズ: 勝敗判定

### 概要

- ルール上継続不能な場合に敗北を確定し、UIへ表示する。

### 実装要件

- 不正デッキ。
- リフレッシュ不能。
- ルール追加時の敗北条件。
- 勝敗表示パネルを `WeissBattleScene` 上に持つ。

### テスト

- 不正デッキで開始前敗北になる。
- 山札/控え室とも空でドロー不能時に敗北できる。

## 5. 必要な新規コンポーネント案

- `BattleSetupConfig`
  - 使用デッキID、プレイヤー種別、先攻後攻決定方式、デバッグ設定を保持。
- `WeissDeckDefinition`
  - 50 枚デッキの定義データ。
- `WeissDeckLoader`
  - `StreamingAssets` / JSON / SQLite からデッキ定義を読込。
- `WeissDeckValidator`
  - 枚数・同名上限・存在しないカードの検証。
- `BattleFlowCoordinator`
  - 対戦準備から勝敗表示までのシーンフローを調停。
- `BattleHudController`
  - 現在フェーズ、手番、操作待ち、勝敗メッセージ表示。

## 6. 既存コードへの主な変更方針

### 6.1 `WeissGame`

- `SetupGame()` から固定ファイルパス依存を除去する。
- プレイヤー生成時に controller 種別を外部設定可能にする。
- 先攻後攻決定を `SetupGame()` または専用セットアップサービスに移す。

### 6.2 `GameManager`

- いまの「生成したら即 `StartGame()`」だけでなく、セットアップ設定を注入できるようにする。
- `RefreshView()` をアクティブプレイヤーだけでなく両プレイヤー表示へ拡張する。

### 6.3 `GameView`

- `Canvas1P` と `Canvas2P` の両方を保持する対戦用ビューに再編する。
- プレイヤー別ゾーンUI参照を持てるようにする。
- 現在手番やフェーズの表示APIを追加する。

### 6.4 `UIGamePlayerController`

- 現在のダミー戻り値を廃止する。
- UI選択待ちを `TaskCompletionSource` ベースで統一する。
- 対戦準備、メイン、アタック、レベルアップ、能力解決の各入力を段階追加する。

### 6.5 `ConsolePlayerController` / NPC

- `ConsolePlayerController` はデバッグ用として残す。
- 本番の `WeissBattleScene` では `SimpleNpcWeissPlayerController` を追加して利用する。

- デッキ定義
- デッキロード
- デッキ検証
- 先攻後攻決定
- 初期手札
- マリガン
- ドローフェーズ遷移

### Step 2. 両プレイヤー表示を成立させる

- `GameView` を 1P/2P 対応
- アクティブ/非アクティブ表示
- フェーズ表示

### Step 3. UI選択系 API を埋める

- 手札選択
- 対象選択
- メインアクション
- 攻撃選択
- レベルアップ選択

### Step 4. NPC定石を実装する

- マリガン
- クロック
- プレイ
- 攻撃
- カウンター
- アンコール

### Step 5. 勝敗導線と回帰テストを整える

- 敗北条件
- 終了演出
- 自動対戦デバッグ

## 8. 受け入れ条件

- `WeissBattleScene` を開いて再生すると、設定済みの両デッキで対戦準備が完了する。
- 不正デッキは開始前に検知される。
- 先攻後攻がランダム決定される。
- 両プレイヤーが初期手札とマリガンを行い、先攻ドローフェーズへ進む。
- ゾーン表示が実ロジックに追従する。
- UIプレイヤーとNPCプレイヤーの組み合わせで対戦進行できる。
